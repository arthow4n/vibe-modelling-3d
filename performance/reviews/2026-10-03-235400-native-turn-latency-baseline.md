# Native turn latency baseline and request timing gaps

Scope: A recent completed repository parent session selected through working-directory metadata on 2026-10-03, using installed Codex CLI 0.160.0. This latency investigation does not establish that the user specifically reported this session as slow or assess an engineering milestone's success. The repository starting revision was `684ed0e`; tested analyzer revision is `dcfa97e`. The baseline was captured during implementation before subsequent regression runs could rotate retained execution history. Private session records and detailed analysis remain local.

Measurements: The snapshot contains 92 unique completed response-usage observations and three completed turns. Native turn first-token delay was measured for all three turns: median 4.014 seconds, maximum 27.803 seconds. This is turn-start to Codex's first recognized model event, which can include eligible reasoning or tool items. Native turn duration had median 1933.912 seconds and maximum 2315.499 seconds. P90 is withheld for these three-observation samples. Request-duration and request-first-token coverage is zero of 92 completed usage observations; throughput is unavailable.

The selected retained engineering execution intervals unioned to 254.508 seconds and overlap agent activity. All selected executions had retained trace coverage, but their agent associations were timing-only: 309 plausible and 49 ambiguous. These are not exact task relationships or complete historical coverage.

Reported input was 10,573,260 tokens, including 10,168,320 cached input tokens; derived uncached input was 404,940. Output was 96,921 tokens, including 39,149 reported reasoning tokens. All four reported categories covered 92 observations and response sums matched the final thread totals. Initial turn configuration was GPT-6.1-sol with high effort for 91 usage observations; the identified compaction response retained unknown configuration. This does not verify request-level model selection or backend implementation. One compaction and no surfaced stream-error/error notices were observed; absent notices do not prove an absence of retries.

Findings: Recorded model-item activity is the largest measured agent category, but its intervals are not complete request timing or isolated inference duration. Initial native delay was sometimes noticeable, but three initial-turn samples cannot characterize the later requests in long turns. Interpretation: the measured admission waits do not support the earlier large-queue explanation for this snapshot. Neither the cached-input/output volume nor unattributed intervals establish slow generation, server scheduling, context occupancy or a specific orchestration cause. Repeated operations may include required checks and regression fixtures; this investigation did not establish avoidable modeling work.

Implications: The analyzer can distinguish observed item activity, tools, compaction and residual time without manufacturing model latency. It cannot rank slow responses or determine token-generation speed from these rollouts. Turn duration and cumulative token usage cannot fill those gaps. A latency inquiry can be useful without making an engineering-productivity claim.

Changes or recommendations: The [workflow contract](../WORKFLOW.md) and existing performance-analysis skill now own the commands, two investigation modes, measurement scopes and coverage rules. Modeling investigations require selected sessions, a bounded period, existing milestone evidence and an explicit association basis. Engineering evidence decides whether revisions/verification were necessary. Native telemetry could improve transport-attempt and reconnect diagnosis, but full response duration, first-token scope and reliable usage association still need qualification for the installed transport. No collector or runtime optimization is justified by this baseline. No inference acceleration is claimed.
