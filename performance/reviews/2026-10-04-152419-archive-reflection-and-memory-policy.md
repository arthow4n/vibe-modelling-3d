The unreserved fixture effectively removes per-job memory accounting by charging one MiB, while retaining job RSS limits, CPU/job admission and the enclosing 2560 MiB process-tree watchdog. Both coordinators were direct children of the experiment so their workers remained within that aggregate watchdog; sampled complete-tree peaks were below 1750 MiB. This is not a test of unlimited memory. Removing memory gating had little additional benefit over the measured 512 MiB budget; separate mode runs and only three batches do not establish a reliable small percentage advantage. Lowering the fixed request to 768 MiB did not improve this four-call group's median over 1024 MiB. There is no universal optimum inferred from these samples.

One immediate unchanged inspection pair, after adding a complete-input declaration, took 18.96 seconds for construction and 0.12 seconds for geometry/artifact reuse at a different destination. Both succeeded and retained matching identities. This single pair demonstrates reuse availability, not a general latency distribution; the existing 60-second idle lifetime still limits reuse across long pauses.

Findings: Memory reservation was a demonstrated avoidable delay. Reducing CPU threads alone retained the old 2 GB memory request. Repeated evidence and the user's requested policy change support reducing the ordinary default, with larger explicit budgets retained.

The four-call investigation exposed concurrent record updates that could overwrite completed metadata. Atomic replacement alone did not serialize read/merge/write operations. Shared record updates now use an interprocess lock; a controlled two-writer regression and complete final policy records qualify that fix. The private benchmark also now launches its coordinator directly: a daemon started by a short-lived evaluator could leave the outer job's monitored process tree after adoption. Earlier four-call measurements were rerun with complete monitoring. This ownership correction is confined to the benchmark.

Contextual review found 20 truncated tool returns and five fillet failure returns in the bounded phase. These are return counts, not unique engineering failures or proven wasted token totals. Large combined reads omitted useful content. Fillet work benefited from identifying tangent seams and treating connected sharp junctions together, rather than repeating radius guesses. An inspection entry point lacked the deterministic declaration already used by printable variants. A render destination was incorrectly treated as repository-relative; correcting a destination need not require rebuilding unchanged geometry.

Form selection advanced into several CAD alternatives before the user expected it. The already-recorded SVG-first preference is the earliest useful intervention. R1's rejected access scoops illustrate why useful access and finger-contact transitions must be reviewed before mechanism refinement. Earlier dome-side and connector failures already have bounded lessons in the object's records: source-card orientation, stable opposing support and complete two-ended capture need checks against actual geometry. Strong grip or a clean slice does not establish alignment or complete product usefulness. The necessary R2 source-card, sparse-occupancy, G/I3/J4 interface, export and slice checks are not classified as waste.

Implications: Ordinary jobs can share limited admission capacity without unnecessarily reserving 2 GB each. Reservations are accounting, not RAM allocation. For managed CAD/scripts the same budget also sets an RSS limit; an overrun stops the job. Four 1 GB-limit jobs could demand more than the 2.5 GB study capacity, so eliminating reservations needs an aggregate limit and a policy for failed work. Existing admission makes excess work wait before starting. The known larger archive check used 551.03 MiB in fresh qualification, excluding a universal 512 MiB default even though that size is adequate for these individual CAD builds. Larger jobs must still request measured headroom. Earlier sketches and focused topology/path diagnosis can reduce repeated CAD effort while retaining the checks needed for a printable object. No additional hood exploration or product variant follows from this reflection.

Changes or recommendations: Implemented a shared 1024 MiB default for CAD evaluation, script execution, script batches and ordinary resource leases. Explicit budgets and geometry-only declarations keep their precedence; explicit native solver-specific budgets are unchanged. Admission capacity and RSS enforcement remain bounded, and failed jobs are not automatically replayed. The current policy is documented in [execution guidance](../../execution/README.md#running-scripts).

Extended the existing [admission benchmark](../admission_benchmark.py) to qualify isometric rendering with fresh views and distinct temporary destinations. Qualified and saved 512 MiB geometry-only budgets for all four R2 sources and the inspection entry point, preserving the 1024 MiB artifact-stage fallback. Added a complete-input declaration to the [archive inspection entry point](../../model/filament_swatch_box_study/inspect_archive_corner_proposals.execution.json). Clarified model-relative render paths, targeted reads after truncation, and the need to freeze repository Python before any CAD batch, including benchmark qualification. Added concrete topology diagnosis to the owning edge-treatment reference and memory-blocker routing to the execution skill. The SVG-first preference was already updated at the modelling handoff and is not duplicated.

The existing admission benchmark now accepts selected budgets and two/four-call batches, with an optional bounded unreserved research fixture. Unreserved admission remains outside ordinary execution: the actual consumer achieves comparable concurrency through the existing smaller-budget declaration, without a new adaptive manager. Concurrent telemetry merges are serialized in the shared writer.

A permanently pre-reserved warm pool was considered. The existing import-only CAD host already stays warm, and deterministic CAD can retain up to two idle workers for 60 seconds or 100 jobs. Idle worker RSS is accounted for and reclaimable. The long measured delay was capacity admission, not allocation of reserved RAM. Keeping full job reservations while idle would reduce available capacity; the immediate inspection reuse measurement already demonstrates useful warm execution. No second pool or permanent idle reservation is added.

Variant builders and card-specific acceptance/lean fixtures remain object-owned. Existing CadQuery, NumPy and shared execution operations cover their concrete needs; extracting another general physics/checking framework would add complexity without demonstrated benefit.
